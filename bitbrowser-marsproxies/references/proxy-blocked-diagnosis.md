# "IP 通但某网站打不开"归因诊断

## 核心方法：对照实验矩阵

只测打不开的那个站 = 只有一组数据，无法归因。必须做对照：

| 实验 | 命令示意 | 验证什么 |
|------|---------|---------|
| ① 直连目标站 | `curl --max-time 8 https://目标站` | 本地网络对该站的态度 |
| ② 走代理访问非封锁站 | `curl -x http://u:p@ip:port http://ip-api.com/json/` | 代理本身活着 + 认证正确 |
| ③ 走代理访问目标站 | `curl -x ... https://目标站/generate_204` | 症状复现 |
| ④ 直连非封锁站 | `curl https://www.baidu.com` | 本地网络基本可用 |

## 判定表

| ①直连目标站 | ②代理+非封锁站 | ③代理+目标站 | 结论 |
|------|------|------|------|
| 通 | 通 | 断 | **本地网络 DPI 阻断明文代理握手**（GFW 类），代理商无辜 → 修复阶梯 |
| 断 | 通 | 断 | 同上（直连断更佐证墙内环境） |
| 通 | 断 | — | 代理认证/协议/端口问题，与封锁无关 → 查凭证与协议开关 |
| 断 | — | — | ②也断 → 代理挂了或本地断网，先修链路 |
| 通 | 通 | 通 | 没问题，浏览器侧缓存/DNS 问题 |

## 沙箱污染教训（血泪）

云端沙箱的出口网络本身可能是受限网络（墙内或企业过滤）：

- 沙箱直连 Google 失败 ≠ Google 有问题，也 ≠ 代理商有问题
- 走代理访问 Facebook/DuckDuckGo/Wikipedia 被 RST，而代理商封锁清单里根本没有这些站 → RST 来自沙箱出口的 DPI，不是代理商
- **任何"谁封锁了谁"的结论必须在用户本机或第二个独立网络复核后才能下**。沙箱内最多只能验证"代理活着 + 非封锁站可达"

## 机理：为什么 GFW 场景下 Google 打不开

HTTP 代理的 `CONNECT google.com:443` 里目标域名是**明文**，中间设备按域名 RST。所以：

- 百度/Bing/ip-api 走同一代理全部正常（目标不在封锁列表）
- Google/YouTube/Facebook 走同一代理全部失败（目标在封锁列表）
- BitBrowser 的 IP 检测（走 ip-api 类）通过——用户以为"代理没问题"，其实只证明非封锁站可达

SOCKS5 的握手请求里目标域名同样是明文，**可能**同样被 DPI，但不一定——值得先试（零成本）。

## 修复阶梯

1. **切 SOCKS5**（零成本）：代理商后台把订单协议从 HTTP 切到 SOCKS5（注意端口可能变），窗口 proxyType 跟着改，用 `https://www.google.com/generate_204` 验收（curl exit 0 且 http_code=204）
2. **加密链式转发**（SOCKS5 也被掐时）：本地起加密隧道，链式转发到代理商代理
   - gost 示例：`gost -L=socks5://127.0.0.1:1080 -F=<加密出口> -F=socks5://user:pass@mars-ip:port`，窗口代理指向 127.0.0.1:1080
   - Clash：用 relay 类型的代理组把「加密节点 → 代理商 socks5」串起来
   - 前提是有一个可用的加密出口（VPS/机场节点）
3. **问代理商**：是否有 CN 优化网关或推荐接入方式（这类代理商中国用户多，通常有方案）

## 验收标准

窗口内访问 `https://www.google.com/generate_204`：返回 204（页面空白即成功）。只看"能连上"不算数，RST 会表现为瞬间失败，curl 用 `--max-time` 兜底防止挂死。
